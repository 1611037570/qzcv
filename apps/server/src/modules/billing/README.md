# 充值计费模块

负责「充值 → 发放凭证 → 凭证扣费」这条链路，并把定价、倍率与毛利红线集中在一处，避免价格散落到业务代码。

**余额归属于凭证本身，不归属于任何推导出来的账户。** 没有 IP、没有设备指纹、没有云端账户：谁拿着凭证，余额就是谁的。因此升级浏览器、切换网络、换设备都不影响已充值的余额；反过来，凭证丢失就是真的丢失，服务端不保存明文，也不提供找回。

## 目录结构

| 文件 | 职责 |
| --- | --- |
| `billing.controller.ts` | 钱包、下单、订单查询、模拟支付、支付回调五类接口 |
| `billing.service.ts` | 凭证生成与校验、订单读写、发放、对话扣费、流水记账 |
| `billing-pricing.service.ts` | 计价引擎：输入/输出分开计价，叠加模型倍率与时段倍率，启动期毛利校验 |
| `billing.sql` | 表结构可读版本，供 DBA 审核或手工建表；服务启动时同样会幂等执行一遍 |
| `dto/create-order.dto.ts` | 下单入参，只接受套餐标识 |
| `payment/payment.types.ts` | 支付渠道适配接口，真实渠道的对接位置 |
| `payment/mock-payment.provider.ts` | 模拟渠道：HMAC 签名回调，本地即可跑通完整发放链路 |

## 数据表

| 表 | 说明 |
| --- | --- |
| `billing_license` | 凭证与余额，只存 `salt + secret_hash`，不存明文；新购一个订单签发一张凭证 |
| `billing_recharge_order` | 订单，金额与到账令牌在下单时快照；`target_key_id` 记录续充目标；`provider_txn_id` 唯一索引兜底重复回调 |
| `billing_license_ledger` | 凭证流水，充值记正数、消耗记负数，每条带余额快照与命中的倍率 |

三张表由服务启动时 `CREATE TABLE IF NOT EXISTS` 自动创建，库不可用时充值接口返回明确原因，不影响对话与导出。

> 早期版本按 IP+UA 推导账户，使用 `billing_account` / `billing_order` / `billing_ledger`，现已废弃，确认无数据后可手工 DROP。

## 新购与续充

- **新购**（本机没有凭证）：支付成功后签发一张新凭证，明文只在该响应出现一次。
- **续充**（下单时带有效凭证）：余额直接累加到该凭证，不签发新凭证，也没有明文可展示。
  这是「少量多次」能成立的前提，否则每次充值都会换成另一张凭证，之前的余额等于从界面上消失。

凭证无效时按新购处理，避免一张过期的本机凭证把购买卡死。

## 凭证格式

```
SF-XXXXXXXX-YYYYYYYYYYYYYYYYYYYYYYYY
   └ 公开部分 ┘ └────── 密文 24 位 ──────┘
```

- 字符集去掉 `I / O / 0 / 1`，避免抄写混淆；前缀 `SF` 便于识别。
- 公开部分用于查库定位，密文只返回给用户一次。
- 服务端存 `sha256(pepper + salt + secret)`，校验时用常数时间比较；凭证不存在与密文错误对外表现一致。
- 输入解析忽略大小写与分隔符，粘贴时不要求格式完全一致。
- 明文只在**发放的那一刻**出现在支付响应里，之后任何接口都不返回。

## 计价规则

所有价格写在 `src/configs/billing.config.ts`，改价需要改代码并重启，不接受前端或数据库下发。

1. **兑换关系**：`1 元 = 200000 计费令牌`（1 令牌 = 5 微元）。
2. **输入与输出分开计价**：默认输入 ¥4 / 百万令牌、输出 ¥16 / 百万令牌，输出更贵。
3. **模型倍率**：`models[模型名].ratio`，未单独配置的模型回退 `default` 并在首次命中时告警。
4. **时段倍率**：夜间 0.9、日间 1.0、晚高峰 1.15，按 `timeZone`（默认 `Asia/Shanghai`）判断小时，容器使用 UTC 也不会错位。
5. **扣费公式**：
   `微元金额 = (输入令牌 × 输入单价 + 输出令牌 × 输出单价) × 模型倍率 × 时段倍率`
   `应扣令牌 = ceil(微元金额 / 5)`，单次最多扣 `maxChargeTokensPerRequest`。
6. **毛利红线**：启动时按「最不利时段 × 最大套餐折扣 × 通道费 × 拒付预提」核算每个模型与套餐的毛利率。出现亏损项直接中断启动；低于目标毛利率只告警。
7. **余额为零不阻断**：凭证缺失、无效或余额为零时继续走免费额度，扣费只在有效凭证且余额大于零时发生，不会出现负余额。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/billing/catalog` | 定价与套餐，不查库也不需要凭证，库异常时仍可展示与购买 |
| GET | `/billing/wallet` | 余额与最近 8 条流水；凭证通过 `x-license-key` 传入，不传时返回未激活 |
| GET | `/billing/ledger?limit=20` | 令牌流水，上限 100 条，需要凭证 |
| POST | `/billing/orders` | 下单，入参 `{ packageId }`；带 `x-license-key` 时续充到该凭证；限流只按来源 IP |
| GET | `/billing/orders/:orderNo` | 查询订单状态，需与下单来源同一 IP |
| POST | `/billing/orders/:orderNo/simulate-pay` | 模拟支付，生产环境默认关闭；**凭证只在该响应返回一次** |
| POST | `/billing/payments/:channel/callback` | 支付渠道异步回调，真实渠道对接入口 |

对话接口 `/llm/stream` 同样读取 `x-license-key`，有效凭证才扣费。

## 上游服务状态（与用户余额无关）

面板顶部的「服务正常 / 服务波动 / 服务异常」来自 `GET /llm/service-status`，反映的是**我们对接的上游**是否健康、额度是否够用：

- 健康度按最近 5 分钟的请求样本统计（失败率、429 次数），由转发层在每次请求结束时埋点，进程内存环形窗口，不落库。
- 额度通过 `OPENAI_BALANCE_URL`（或 DeepSeek 官方地址自动推导的 `/user/balance`）查询，结果缓存 60 秒；上游没有额度接口时显示「未开放查询」，不影响服务判定。
- 接口只返回一个状态结论，不返回模型名、额度数值、请求量与上游地址；额度只用于服务端判定「还能不能继续提供服务」。

## 接入真实支付

1. 新建一个实现 `PaymentProvider` 的提供者，实现 `create` 与 `parseCallback`；`parseCallback` 必须基于原始请求体验签（`main.ts` 已通过 `json({ verify })` 保留 `rawBody`）。
2. 在 `billing.module.ts` 把 `PAYMENT_PROVIDER` 指向新实现，删除或保留 `MockPaymentProvider` 均可。
3. 渠道后台配置回调地址 `/billing/payments/<channel>/callback`。
4. 生产环境设置 `BILLING_MOCK_PAYMENT=0`，模拟支付接口会直接拒绝。

订单状态流转固定为 `待支付 → 已支付 → 已发放`，两步都用条件 `UPDATE` 判断影响行数，配合 `provider_txn_id` 唯一索引保证「一单只发一张凭证」。

## 前端配合

> 内置服务当前未上线：`apps/web/src/configs/modules/ai.ts` 的 `builtinServiceEnabled = false` 时，服务商列表不出现雪花服务、store 也不再注入内置模型，角色上的历史绑定会自动失效。后端接口与数据表保持可用，把开关改回 `true` 即恢复上线，无需改服务端。

- 凭证保存在 `localStorage`（键 `snowflakeAiLicense`），充值成功后自动写入一份。
- 面板把「服务状态 / 余额 / 套餐」拆成三个独立请求：余额接口失败只影响余额卡片，套餐走 `/billing/catalog` 仍可正常购买；充值不可用由品牌卡的状态胶囊提示，不在余额区喊。
- 重试采用「保留错误内容 + 按钮进入重试态」，不会出现错误框被关掉的闪烁。
- 充值成功弹窗把凭证完整展示一次，并提示「服务端不保存明文、清除浏览器数据会丢失、建议少量多次充值」。
- 购买套餐前就会展示「没有云端账户」的说明，避免用户一次性充太多。
- 对话请求由 `getAgentLLM` 注入 `x-license-key`，没有凭证时不带该头。

## 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `BILLING_MOCK_PAYMENT` | 生产 `0`，其余 `1` | 是否允许模拟支付；生产默认关闭，需要联调时显式设 `1` |
| `BILLING_MOCK_SECRET` | `snowflake-mock-pay` | 模拟渠道签名密钥，仅开发使用 |
| `BILLING_LICENSE_PEPPER` | `snowflake-license-pepper` | 凭证哈希密钥，**生产必须改成独立随机值**；更换后所有旧凭证立即失效 |
| `LLM_MAX_OUTPUT_TOKENS` | `4000` | 单次请求输出令牌上限，外部传入更大的 `max_tokens` 会被向下钳制 |
| `OPENAI_BALANCE_URL` | 空 | 上游额度查询地址；留空时只对 `api.deepseek.com` 自动推导，其他中转不探测 |
| `OPENAI_QUOTA_LOW_YUAN` | `20` | 上游余额低于该值（元）判定为「额度偏低」 |

## 已知限制

- 凭证是唯一凭据，丢失无法找回；服务端只保留哈希，运营也只能看到订单号与凭证公开部分，无法还原完整凭证。这是「无账号 + 无云端保存」的必然结果，所以产品文案必须持续提示「少量多次」。
- 当前是「先放行后结算」：余额不足以覆盖一次请求时扣到零为止，本次不追扣，也不会拦截请求。
- 订单限流按来源 IP，`x-forwarded-for` 由 Nginx 写入；若 Nginx 采用追加而不是覆盖，客户端可以伪造首段 IP。
